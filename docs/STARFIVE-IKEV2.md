# StarFive: экспериментальный IKEv2/IPsec

В версии 0.2.20 появился раздел «Экспериментальное». Режим включается явно,
требует персональный профиль с сертификатом и установленный strongSwan.
Обновление клиента само по себе не устанавливает strongSwan и не включает этот режим.
Основные поддерживаемые клиентом дистрибутивы — Arch и Fedora; новая функция
пока требует проверки на настоящем ноутбуке. Fedora с SELinux в этом выпуске
отдельно не проверялась.

Схема первого этапа: ноутбук → IKEv2/EAP-TLS → StarFive в России → интернет.
Эстонский выход и Xray на шлюзе ещё не настроены. Это техническая реализация
стандартного протокола, а не государственная сертификация или гарантия
доступности у всех российских операторов.

## Тест на ноутбуке

1. Выполнить `vpn update`, закрыть и заново открыть Evgenium Network.
2. Перенести персональный `profile.json` в `~/Vpn/StarFive/profile.json`.
   Файл содержит приватный ключ. Он предназначен для одного устройства,
   не должен попадать в GitHub, публичные логи или сообщения.
3. Отключить обычный VPN. Открыть «Экспериментальное», нажать
   «Подготовить IKEv2», затем «Импортировать». Подготовка устанавливает
   пакет strongSwan средствами дистрибутива; может потребоваться несколько минут.
4. Включить переключатель подключения к StarFive.
5. Проверить `vpn status` и `vpn experimental status`: VPN должен быть активен,
   IPv6 заблокирован, kill switch активен. Внешний IPv4 должен быть
   `109.194.67.159`. Проверить несколько сайтов, видео и загрузку большого файла.
6. Повторить через мобильную точку доступа. Это проверит внешний маршрут,
   а не только работу внутри домашней сети.
7. При проблеме с сайтом ввести **только домен** в поле проверки и отправить
   отчёт. HTTPS-проверка подтверждает соединение и ответ сервера; она не
   гарантирует работу видео, авторизации и других функций сайта.
8. Для теста защиты выполнить `sudo systemctl stop evgenium-ikev2.service`.
   Открытие новых внешних соединений должно прекратиться. `curl -4 --max-time 8
   https://www.cloudflare.com` должен завершиться ошибкой. После этого
   выполнить `vpn experimental off` — обычный интернет должен восстановиться.

При любой проблеме восстановление: `vpn experimental off`.
Для следующей попытки снова включить режим. Автоматического переподключения
пока нет. При перезагрузке после аварии защита сохраняется: явно выключить
режим перед обычным использованием сети. Не удалять nftables вручную.

В экспериментальном режиме DIRECT-исключения, Waydroid и пересылка трафика
других устройств не поддерживаются. Доступ к домашней сети шлюза закрыт.

## Диагностика на время тестирования

После импорта профиля временная диагностика включена; её можно выключить
переключателем или `vpn experimental telemetry-off`. Каждую минуту проверяются
example.com, www.wikipedia.org и www.youtube.com. Ручная проверка отправляет
введённый домен. Автоматического наблюдения за всеми сайтами браузера нет.

Коллектор хранит домен проверки, её результат, HTTP-код, суммарную задержку,
версию manager, время приёма и псевдоним сертификата. Полные URL, содержимое
пакетов, имена пользователя, исходный IP, пароли и приватные ключи в отчёты
не включаются. Домены, время и устойчивый псевдоним всё равно являются
псевдонимными, а не полностью анонимными данными.

Отчёты передаются только внутри VPN по HTTPS с взаимной проверкой
сертификатов. Порт 8443 не пробрасывается на роутере. Файлы сервера:
`/var/log/evgenium-experimental/YYYY-MM-DD.jsonl`, права root-only,
хранение около 7 дней, лимит 8 МиБ в сутки.

Отключить приём отчётов глобально на StarFive:

```bash
sudo rm -f /etc/evgenium-diagnostics-enabled
```

Удалить накопленные отчёты (необратимо):

```bash
sudo find /var/log/evgenium-experimental -type f -name '*.jsonl' -delete
```

Сервис коллектора оставляют работающим: его `/health` нужен для подтверждения
подключения и работает без записи отчётов. Отключение диагностики не делает
пользователя невидимым для посещаемых сайтов или сетевых операторов.

## Управление сервером

Администратор выпускает отдельный 30-дневный профиль каждой тестовой машине:

```bash
sudo evgenium-issue-device
```

Команда выводит путь к секретному JSON. Передавать его владельцу устройства
защищённым способом; публичный релиз не содержит пользовательских профилей.

Отозвать потерянный профиль:

```bash
sudo evgenium-revoke-device device-0123456789abcdef01234567
```

Отзыв обновляет CRL для IKEv2 и HTTPS, а также завершает существующие тестовые
VPN-сессии. Остальные устройства могут подключиться заново.

Развёртывание шлюза: прочитать `server/setup-starfive.sh` перед запуском.
Скрипт предназначен **для этого выделенного StarFive**: он заменяет firewall,
включает IPv4 forwarding и использует eth0, UDP 500/4500 и пул 10.77.0.0/24.
На произвольном сервере его без адаптации запускать нельзя.

Проверка выполнена на Debian 13 / RISC-V внутри отдельного network namespace
на StarFive: EAP-TLS, AES-256-GCM, NAT-T, DNS, HTTPS через интернет,
доставка mTLS-отчёта, блокировка IPv6 и трафика после остановки IKE-демона.
Это не заменяет тест с ноутбуком через внешнего оператора и тест всех клиентских
служб systemd/DNS на Arch/Fedora.

## Глобальный тест стабильности (0.2.21)

Кнопка «Глобальный тест» запускает фоновую проверку примерно на 4–8 минут,
с расходом до 200 МиБ. Нужны активный StarFive VPN и включённая временная
диагностика. Интернет несколько раз прервётся намеренно; kill switch
всё время сохраняется. «Остановить тест» отменяет дальнейшие проверки.
CLI: `vpn experimental global-test` / `vpn experimental cancel-test`.

Проверяются:

- HTTPS-проверки Яндекса, Mail и Ростелекома до и после нагрузки,
  а также контрольные проверки тех же сервисов с самого StarFive.
- Задержка, разброс и потери ICMP до VPN-шлюза с размерами 56/1200/1360 байт
  и запретом фрагментации. ICMP сам по себе не доказывает потерь TCP/UDP.
- Серия коротких HTTPS-соединений к шлюзу.
- Скачивание до 32 МиБ, отправка до 4 МиБ и проверка размеров/SHA-256.
  Используются только синтетические данные, личные файлы не читаются.
- Прерывание загрузки 8 МиБ после 3 МиБ, переподключение и докачка HTTP Range
  с проверкой содержимого обеих частей по независимо известному шаблону.
- Два параллельных скачивания и одновременная отправка.
- До минуты повторной передачи с ограничением общего объёма 64 МиБ.
- 45 секунд простоя и проверка восстановления активности.
- Пять повторных подключений, затем остановка/запуск собственного VPN-демона.
  Во время остановки проверяется сохранность guard и отсутствие TCP-доступа
  к предварительно разрешённому IPv4 Яндекса.
- Счётчики IPsec, общесистемных TCP retransmissions и XFRM до/после,
  а также CPU, доступная память и ошибки/потери Ethernet на StarFive.

Внешние проверки обращаются только к yandex.ru, mail.ru и www.rt.ru,
без перехода по редиректам. DNS — базовый Яндекс DNS 77.88.8.8 / 77.88.8.1.
Тяжёлые загрузки идут между клиентом и собственным российским StarFive,
а не на сторонние публичные сайты. Прежние зарубежные периодические проверки
в 0.2.21 заменены на российские. Старый клиент до обновления сохраняет старую
логику проверок.

Отчёт `event=global_test` содержит только ограниченные числовые метрики,
результаты проверок, названия разрешённых российских сервисов и случайный
идентификатор запуска. Сервер добавляет псевдоним сертификата и время.
Сырые логи, адреса клиентов, URL, имена процессов и содержимое файлов не
отправляются. Отчёт хранится в тех же root-only JSONL с прежним сроком хранения.

Если результат не удалось отправить, он остаётся root-only в
`/etc/vpn-manager/starfive/pending-global-test.json`; при включённой диагностике
попытка повторяется после восстановления VPN. Если диагностика выключена,
отправка не выполняется. Прогресс хранится в
`/var/lib/vpn-manager/starfive-test.json` и показывается в интерфейсе.

Результаты помогут отличить проблемы самого моста от проблем выхода StarFive
к сервисам и перегрузки платы. Они **не доказывают намеренное ограничение
провайдером**. Для такого вывода нужны сравнение с обычным интернетом,
повтор через другого оператора и сопоставимые условия. Встроенный тест
не выключает защиту ради прямого контрольного соединения. Счётчики TCP
относятся ко всему клиентскому хосту: фоновая активность других приложений
может влиять на них. HTTP 403/429 учитывается как ответ сервера, а не как
обрыв VPN; пригодность самого сайта для браузинга здесь не проверяется.
