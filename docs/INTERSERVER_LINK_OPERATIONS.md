## Устройство

Один WireGuard IP-оверлей: Эстония `10.203.71.1/30`, StarFive `10.203.71.2/30`, интерфейс `evg-wg`, MTU 1280. На StarFive интерфейс находится в `evg-link`, а его UDP-сокет создан в основном network namespace. В пространстве `evg-link` нет другого внешнего интерфейса: остановка туннеля не открывает прямой выход.

Проверены три способа доставки того же WireGuard-потока. По первому сравнительному окну выбран основной `tcp`, резерв `hy`; это предварительный выбор до суточного наблюдения:

- `direct`: обычный UDP к Эстонии:24447.
- `hy`: UDP через отдельный Hysteria 2.13.0/Salamander, публичный UDP24446, локальный relay StarFive 127.0.0.1:24445. TLS с проверкой собственного сертификата. Сохраняется полноценный IP-оверлей WireGuard; возможности IP не приписываются самому прокси.
- `tcp`: доставка через отдельный Xray 26.7.11/VLESS/TLS, публичный TCP24443, локальный relay StarFive 127.0.0.1:24449. Прокси передаёт исключительно UDP к собственному WireGuard-порту (временный диагностический relay удалён после сравнений). Это отдельный бинарник/конфиг/unit, не Xray панели.

Полноценный TCP/UDP-выход в интернет из пространства StarFive идёт через NAT Эстонии. Внешний IP подтверждается отдельно. IPv6-выход не предоставляется: на серверах нет глобального IPv6/default route, у пространства нет обходного IPv6-пути. Весь компьютер пользователя к этому каналу не подключён.

## Изоляция

- Рабочий `x-ui.service`, PID панели и дочернего Xray, конфигурация `/usr/local/x-ui/bin/config.json` проверяются отдельно. Не останавливать/обновлять эти процессы, не использовать их inbound, UUID, ключи, базу или сертификаты.
- На StarFive не изменяются существующий strongSwan, pool 10.77/24, table/rule 220, enrollment, PKI/CA и коллекторы.
- Главные default routes и DNS не изменены. DNS пространства: `/etc/netns/evg-link/resolv.conf`, 1.1.1.1 и 9.9.9.9.
- На VPS включён forwarding только на `eth0` и `evg-wg`. Глобальный `net.ipv4.ip_forward` остаётся 0. Это позволяет не применять сброс общих IPv4 sysctl, происходящий при изменении глобального ip_forward. Собственная цепь запрещает посторонний транзит и выход туннеля в частные/служебные сети.
- Собственные nftables-таблицы на VPS: `inet evg_link`, `ip evg_link_nat`; на StarFive — `inet evg_link_transport` только для выделенного UDP24444; никаких flush общих таблиц. Динамический fail2ban сохраняется. Сохранён исходный per-interface forwarding для отката.
- Ключи/пароли/сертификаты стенда — `/etc/evgenium-link`, root-only. Приватные ключи WireGuard и TLS созданы на соответствующих серверах. Закрытый ключ старой CA не читался и не экспортировался.
- Бинарники в `/opt/evgenium-link`, runtime/снимки в `/var/lib/evgenium-link`, журналы в `/var/log/evgenium-link`. Нативные wireguard-tools извлечены из пакетов без установки. Hysteria/Xray скачаны из официальных релизов, проверены SHA-256 asset digest.

## Автовосстановление

`transport.py` на StarFive атомарно обновляет собственную nft-таблицу допуска к UDP-сокету WireGuard, затем задаёт endpoint и сохраняет режим. Пакеты от невыбранного relay отбрасываются: иначе WireGuard roaming может вернуть прежний путь по запоздавшему аутентифицированному пакету. Health сравнивает фактический endpoint с режимом и исправляет устойчивое расхождение. Одного файла mode недостаточно для подтверждения используемого транспорта.

`evgenium-link.service` создаёт/удаляет только собственный интерфейс и правила. Пустое пространство на StarFive сохраняется после stop для fail-closed поведения уже запущенных процессов.

`evgenium-link-health.timer` запускает проверку через 5 секунд после завершения предыдущей (сам запрос и планирование добавляют время), проверяет локальный интерфейс, внутренний ping и отдельно внешний HTTPS/ожидаемый IP. Один сбой сайта не перезапускает канал. При внутреннем отказе дополнительно записываются физический линк, маршрут, ответы gateway/underlay, возраст рукопожатия и состояние своих транспортов. Внешний HTTPS проверяется не чаще раза в минуту; при ошибке добавляется независимый контрольный сервис. StarFive после трёх последовательных неудач внутренней передачи переключает транспорт; Эстония чинит только отсутствующий/опущенный собственный интерфейс. Смена внешнего транспорта сохраняет внутренние адреса и NAT-выход, но сохранение каждой TCP-сессии при любом отказе не гарантируется.

Ограничения: максимум 5 действий восстановления в час, backoff, минимум 5 минут между сменами транспорта, без автоматического возврата на основной транспорт только ради предпочтения. Файл `/var/lib/evgenium-link/mode` хранит текущий режим, `preferred-mode` — предпочитаемый UDP-вариант при уходе с TCP (по умолчанию `hy`). Файл `resource-hold` также блокирует запуск собственных link/transport units после перезагрузки до ручного разбора. Файл `maintenance` временно подавляет только собственные health/recovery действия для контролируемых испытаний. Не оставлять его после работ.

`evgenium-link-services.timer` на StarFive раз в пять минут проверяет DNS UDP/TCP, ожидаемый egress, Discord API/CDN/Gateway WebSocket и HTTP-доступность других контрольных сервисов. Он использует защищённое пространство и не зависит от временного диагностического сервера. Health и ресурсные проверки работают независимо от приложения Codex.

Службы транспортов имеют собственные лимиты памяти/CPU, Restart=on-failure и ограничение частоты. Эти лимиты не ограничивают весь kernel/softirq; дополнительно используются ограниченные генераторы трафика и наблюдение за хостом. Общий интерфейс eth0 не шейпится.

## Управление

Команды выполняются локально на соответствующем сервере с root-правами.

```bash
systemctl status evgenium-link evgenium-link-hy evgenium-link-tcp evgenium-link-health.timer
# StarFive: ручная проверка трафика внутри защищённого пространства
ip netns exec evg-link ping -c 3 10.203.71.1
ip netns exec evg-link /opt/evgenium-link/package/usr/bin/wg show
# StarFive: ручной выбор пути через тот же механизм, что у автоматики
python3 /opt/evgenium-link/transport.py tcp
# Значения: tcp, hy, direct. Перед выбором TLS-транспорта убедиться, что его service активен.
# Не задавать endpoint отдельно от собственного фильтра.
# Не использовать wg show ... private-key или dump в общих журналах.
```

Чтобы намеренно остановить канал, сначала остановить его таймер восстановления, затем собственные службы. При срабатывании защиты по ресурсам также создаётся `resource-hold`, который запрещает автозапуск до ручного разбора. Иначе recovery будет пытаться восстановить удалённый интерфейс.

```bash
systemctl stop evgenium-link-health.timer
# Только на StarFive:
systemctl stop evgenium-link-services.timer
systemctl stop evgenium-link
systemctl stop evgenium-link-hy evgenium-link-tcp
```

Для полного удаления требуется также остановить и отключить `evgenium-link-resource.service`, выполнить disable перечисленных собственных units и удаление только перечисленных собственных файлов/таблиц. Не восстанавливать сохранённый полный nft ruleset поверх текущего fail2ban. На VPS stop возвращает сохранённое значение `eth0.forwarding`; если после установки администратор намеренно изменял forwarding для других задач, сначала согласовать владение этой настройкой.

После срабатывания `resource-hold` сначала устранить причину перегрузки. Затем вручную удалить только этот файл, выполнить `systemctl reset-failed` для собственных link/hy/tcp units и запустить их вместе с resource-службой и health-таймером. На StarFive также проверить services-таймер. Само удаление hold не должно считаться устранением причины.

Сертификат собственных TLS-транспортов истекает 17 октября 2027 в 19:48:04 UTC; health ежедневно проверяет запас 30 дней и записывает предупреждение в журнал; до истечения требуется согласованное обновление публичного доверенного сертификата на StarFive. Ключи/сертификаты панели для этого не используются. Одна пара серверов остаётся общей точкой отказа по электропитанию, провайдеру и доступности VPS.

## Методика и ограничения измерений

Основной прогон 65 минут: внутренний ping каждые 15 секунд, короткие UDP-серии, DNS UDP/TCP, ожидаемый egress, Discord API/CDN/Gateway WebSocket, YouTube, GitHub, Telegram, Cloudflare. Передача 256 KiB в каждую сторону с проверкой содержимого и ограничением примерно 1 Мбит/с. Отдельные равномерные UDP-пробы: 160 байт каждые 20 ms. STUN проверяет внешний UDP-выход. Успешный WebSocket HELLO без входа в аккаунт не является реальным голосовым звонком Discord.

Сбой корня CDN с HTTP403 на начальном preflight не считался сетевой неисправностью: основная проба использует существующий публичный avatar asset. Накопительные счётчики и старые измерения не выдаются за свежие. Управляемые потери, удаление интерфейса, остановка транспорта, смены режима и idle-окна записываются на отдельной временной шкале и отделяются от обычных отказов.

## Журналы и продолжение проверки

`health.jsonl` на каждом узле и `services.jsonl` на StarFive ограничены 1 MiB на текущий файл плюс три ротации. `resources.jsonl` — 2 MiB плюс три ротации: этого хватает для полного суточного окна при текущем размере записей. Итого до 16 MiB постоянных JSON-журналов на StarFive и 12 MiB на VPS. Разовые `probes.jsonl`, `events.jsonl` и результаты сравнений сохраняются после теста как ограниченные по времени артефакты. Не включать access logging прокси с клиентскими адресами. Приватные конфигурации и ключи не копировать в отчёты.

Защита ресурсов при трёх подряд 10-секундных выборках с общей занятостью CPU >50% либо свободной памятью <1 GiB на VPS / <2 GiB на StarFive останавливает собственный канал и ставит `resource-hold`. Это сознательный приоритет сохранения действующего сервиса. Сам факт остановки требует разбора; снимать hold автоматически без проверки причины нельзя.

Автозапуск проверяется через systemd enable и зависимости. Реальная перезагрузка общего VPS не выполняется: это нарушило бы ограничение сохранения активных клиентов. Максимальная пропускная способность, реальные Discord-звонки и 24–72 часа стабильности не считаются доказанными часовым прогоном.
