# Экспериментальный VPN через StarFive и Эстонию

**Проверка на 18 октября: исправление локального DNS восстановило WebSocket отдельного GUI Codex через реальный туннель StarFive → Эстония. Повторное полное переключение основного рабочего стола после исправления не проводилось; это остаётся границей проверки версии 0.3.1.**

Версия 0.3.1 добавляет общий режим: компьютер → IKEv2/EAP-TLS → StarFive → существующий WireGuard через независимый VLESS/TLS либо Hysteria → Эстония.

После `vpn update` закройте и откройте приложение. В «Экспериментальное» сохраните существующий токен и нажмите «Подключить». StrongSwan, conntrack-tools и остальные системные зависимости устанавливаются автоматически на поддерживаемых Arch/Fedora. Обновление и установка зависимостей сами экспериментальное подключение не включают.

Ключ устройства создаётся локально. Токен передаётся через stdin служебного процесса; интерфейс показывает только короткий идентификатор. Ранее выданные токены и сертификаты продолжают работать.

## Поведение

При подключении клиент сначала проверяет StarFive и эстонский выход в отдельном network namespace, затем включает защиту, останавливает обычный Xray этого менеджера и направляет IPv4-трафик компьютера через экспериментальный канал. DIRECT-списки обычного VPN не импортируются и не изменяются. IPv6 блокируется. DNS TCP/UDP 53 направляется через туннель; при systemd-resolved DNS назначается только выделенному интерфейсу; в остальных системах исходный resolv.conf сохраняется и восстанавливается при явном отключении.

Прямых исключений для SSH, приложений и уже открытых соединений нет. DHCP broadcast сохраняется для получения адреса физического подключения. IPv4-трафик контейнеров также направляется через туннель; иной транзит блокируется. Существующие серверы на компьютере могут стать недоступны снаружи во время полного VPN.

IKEv2 остаётся в отдельном network namespace, чтобы локальные VPN/серверы с адресом 10.77.0.1 не конфликтовали с внутренней диагностикой StarFive. Veth с MTU1280 передаёт пользовательский трафик в namespace. NAT к выданному виртуальному адресу выполняется перед IPsec; фильтр netdev egress разрешает на внешнем интерфейсе namespace только IKEv2 и служебное обращение к StarFive, блокируя незашифрованный обход при потере SA.

При неожиданном завершении клиента защита, запретный маршрут и DNS остаются. «Починить» повторяет подключение. «Отключить» снимает защиту и возвращает исходный DNS; обычный VPN затем можно включить вручную. Перезагрузка не включает эксперимент автоматически, но сохраняет блокировку после аварийного завершения до явного отключения или восстановления.

## Ретранслятор

StarFive направляет только аутентифицированный пул IKEv2 10.77.0.0/24 через собственную таблицу 51827 в namespace evg-link. NAT в namespace приводит источник к 10.203.71.2, поэтому конфигурация WireGuard и правила выхода на эстонской стороне не меняются. Служба evgenium-relay и её проверка работают отдельно от strongSwan. Остановка ретранслятора оставляет блокировку, не возвращает российский прямой выход.

Собственная таблица evg_relay_guard также загружается через include в nftables.conf до запуска сетевых служб. Reload firewall может временно остановить ретрансляцию до следующей проверки, но не разрешает обходной выход. Восстановление ограничено пятью попытками в час. Режим resource-hold не снимается автоматически.

Рабочая 3X-UI и её Xray не перезапускаются и не перенастраиваются. Межсерверная схема и её ограничения описаны в INTERSERVER_LINK_OPERATIONS.md.

## Границы проверки

Сквозной стенд проверяет реальный IKEv2, ретрансляцию, NAT, DNS UDP/TCP, HTTPS, Discord Gateway WebSocket и блокировку после отказов. Этот стенд расположен на StarFive; он не измеряет путь пользователя через независимого российского провайдера. Успешный WebSocket не доказывает качество авторизованного голосового звонка Discord. Результаты проверки реального компьютера фиксируются отдельно после испытания.

Исправлена отдельно воспроизведённая ошибка смены DNS: старые записи NAT сохранялись после удаления правил и удерживали открытый UDP-сокет на DNS предыдущего VPN. Клиент удаляет только устаревшие DNS-перенаправления этого менеджера, без очистки остальных соединений. Изолированная проверка `scripts/test-dns-transition.py` проверяет переход туда и обратно на том же сокете. Это не является подтверждением восстановления Codex на полном маршруте.

18 октября отдельно воспроизведено повреждение локального DNS stub: прежний DNAT перехватывал 127.0.0.53 и отправлял loopback-пакеты на veth. Исправление сохраняет loopback DNS, а исходящие запросы резолвера по-прежнему ограничены туннелем. Перед состоянием «Подключено» проверяются и системный DNS по resolv.conf, и HTTPS. `scripts/test-local-dns-guard.py` проверяет старый сбой и исправление средствами ядра Linux. В отдельном GUI Codex с локальным UDP stub старые правила дали EAI_AGAIN; атомарная замена правил восстановила WebSocket без перезапуска GUI. Выход — 38.180.164.67. Основной рабочий стол в этой проверке не переключался; его прежний тайм-аут рукопожатия пока не проверен повторно.
