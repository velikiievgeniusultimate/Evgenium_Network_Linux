# Проверяемые резервные маршруты

Эксплуатационные компоненты RU↔EE. Это не клиентская система рейтинга и не
обновление клиентского пакета. Существующий зашифрованный WireGuard-канал
сохраняет внутренние адреса при смене транспорта.

- `path-probes.py` создаёт отдельную WG-идентичность и пространство сети для
  каждого маршрута. Проверка отвечает на вопрос, проходит ли именно этот путь,
  даже когда рабочий канал использует другой транспорт. Сервер разрешает этим
  адресам только необходимый ICMP; это не клиентский выход в интернет.
- `resilient-health.py` переключает рабочий канал только на путь с двумя
  успешными независимыми пробами. Два провала рабочего канала инициируют выбор;
  между переключениями минимум шесть секунд. Возврат к предпочтительному пути
  требует 180 секунд и 90 успешных проверок. Файлы `maintenance` и `resource-hold`
  запрещают действия. Зависший транспорт после шести неуспешных отдельных проб
  перезапускается не чаще раза в 120 секунд; работающий канал не перезапускается
  из-за одной лишь неисправности проверочного пути.
- `home-bridge.py` принимает только localhost и ограничивает число потоков
  восемью. Каждый идёт через отдельный SSH-ключ с закреплённым host key.
  `home-stdio.py` — принудительная команда этого ключа на резервном узле; она
  передаёт поток только в фиксированный TLS-порт Эстонии. SSH forwarding,
  оболочка и произвольные адреса ключу не предоставляются.
- `flight-recorder.py` пишет ограниченное кольцо пакетов физического канала;
  при повторном отказе сохраняет снимки и короткий полный захват. Фильтр должен
  содержать только зашифрованные межсерверные транспорты и служебный ICMP.
  Не захватывать расшифрованный клиентский интерфейс. Каталоги и журналы закрыты
  от обычных пользователей; действует ротация.

Перед развёртыванием требуются существующий собственный WG-канал, отдельные
конфигурации транспортов, проверенные host keys и systemd units. Эти файлы не
являются универсальным установщиком. Не изменять чужие Xray/3X-UI, SSH-сервер,
главные маршруты или DNS. Не проверять внешний SSH-порт частыми TCP-коннектами:
это расходует лимит новых SSH-соединений и может заблокировать резервный путь.

Испытательный клиент размещён на StarFive и управляется по LAN. Переключения
VPN, отказы и нагрузочные тесты на рабочем компьютере владельца запрещены.
Скорость StarFive ограничена его CPU и не является оценкой потолка x86-клиента.

Проверка логики: `python -m unittest discover -s tests -p test_server_resilience.py`.

## VLESS + REALITY и XHTTP

Дополнительные независимые службы: `evgenium-link-reality` и
`evgenium-link-xhttp` на RU; `evgenium-carrier-reality` и
`evgenium-carrier-xhttp` на EE. Они передают зашифрованные WG-пакеты,
не возвращают старый клиентский интерфейс профилей VLESS.
Отдельный бинарник и конфигурации EE находятся в `/opt/evgenium-carriers`
и `/etc/evgenium-carriers`; рабочий 3X-UI не перезапускается.

Примеры `reality-*.example.json` и `xhttp-*.example.json` требуют новых UUID,
ключей REALITY, short ID и пути XHTTP. Это шаблоны, не готовые секреты.
EE TCP 24575/24576 ограничены firewall источником RU; RU слушает только
127.0.0.1 UDP 24555/24557. Выход Xray разрешает только UDP 127.0.0.1:24547
через точный `finalRules`, остальные назначения блокируются. Разрешение
нужно и в routing, и в freedom: новые Xray блокируют частные адреса по умолчанию.

Проверки: `evg-probe-reality` / `evg-probe-xhttp`, отдельные WG-ключи,
адреса 10.203.90.5/.6. Перед добавлением в выбор нужно расширить `probes.json`
на обоих серверах и `/opt/evgenium-link/transport.py` соответствующими
localhost-портами. Предпочтительный маршрут задаётся отдельно; наличие
REALITY/XHTTP само по себе не доказывает преимущество по скорости.
Первый handshake может занять несколько секунд. Не включайте `realitySettings.show`
на постоянной основе: отладочный вывод содержит материал рукопожатия.

В проверенной конфигурации XHTTP используется `stream-one`: короткий прогон
показал около 115/7 Мбит/с против 79/3 Мбит/с у `packet-up` на более длинном
прогоне. Размеры и время различались, поэтому это ориентир для выбора резерва,
а не строгое доказательство превосходства режима. Обёрнутые каналы по отдаче
существенно уступают контрольному TCP между теми же серверами (примерно
250/309 Мбит/с на 16 МиБ в каждую сторону). Лимит отдачи остаётся предметом
диагностики; новые транспорты не назначены предпочтительными.
